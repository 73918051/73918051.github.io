平台模型与关键考点
平台：64 位，小端序；char=1、int=4、指针=8。
FILE 类型：系统库内部结构体；fp / fg 是 8 字节句柄地址，示意值 0x5A2C / 0x6B3E / 0x7C4F。
★ "a+" 追加模式：
　a = append：文件不存在则新建；已存在则保留原内容，新数据写到末尾（不清空！）
　+ = 可读可写
　打开时读写位置自动在文件末尾——所以 fputs 不用 fseek 就自动追加
　若错写成 "w" / "w+"，已有内容会被立刻清空！
★ *++argv 求值顺序：++（前置自增）优先级高于 *（解引用）
　所以 *++argv = *(++argv)：先移动指针，再解引用
　绝不能写成 (*argv)++——那是对字符指针本身做自增
★ argc = argc - 2：减去程序名（1）+ 目标文件名（1）= 剩下源文件个数
　隐患：破坏了 argc 的原始值，后续无法再查询参数总个数
★ while(argc--) 后置自减：
　① 取当前值作为「本轮判断依据」→ ② 立刻减 1（不管判断结果）→ ③ 用 ① 决定是否进入循环体
　轨迹：2 → 1（第 1 轮）→ 1 → 0（第 2 轮）→ 0 → -1（假，退出）
　退出后 argc = -1（副作用）
★ 【核心 Bug】while(!feof(fg)) 经典陷阱：
　feof 只在一次读取尝试失败之后才返回真——它描述的是「过去」，不是「未来」
　所以循环必然多跑一次：最后 fgets 返回 NULL，但循环体已进入，fputs 仍被调用
　后果：out.txt 里每行被重复写入一遍
★ fgets 返回 NULL 时缓冲区未变：
　C 标准原文：「缓冲区内容未指定」；
　glibc 实际行为：不修改缓冲区——所以 s 里残留上次读到的内容
　这正是重复写入 Bug 的根本原因（依赖实现的行为，不是设计）
★ fputs(fgets(...), fp) 读写合并：
　外层 fputs 直接接收内层 fgets 的返回值——「读一行 + 写一行」一条语句完成
　隐患：如果 fgets 返回 NULL，fputs(NULL, fp) 本应崩溃，
　但因 s 未被修改，「恰好」会用到残留内容——依赖未定义行为的巧合
★ #define B 128：预处理阶段替换；fgets(s, B, fg) 最多读 127 字符 + \0
　好处：可读性（一眼看出是缓冲区大小）+ 可维护性（改一处全部生效）
优点：两处 fopen 都做了判空——比很多教科书程序写得好
缺陷：源文件打开失败时直接 return 0，目标文件 fp 没关闭——资源泄漏
★ 正确写法：while (fgets(s, B, fg) != NULL) fputs(s, fp);
★ fgets / fputs 与 gets / puts 对比：
　gets 不限制长度、会溢出、已废弃；scanf("%s") 读不到带空格的整行；
　fgets 安全、能读整行、带长度限制；
　puts 自动补换行；fputs 不补换行，遇 \0 停
★ 终端输出：本程序成功路径下没有任何 printf——所有数据都写到了 out.txt
复杂度：时间 O(文件总行数)，空间 O(1)（一个 128 字节固定缓冲区）
